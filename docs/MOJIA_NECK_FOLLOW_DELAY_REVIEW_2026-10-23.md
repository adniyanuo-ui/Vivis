# 墨甲眼头跟随延迟核查（2026-10-23）

## 1. 结论与范围

最新180秒测试正常完成。已确认存在秒级的眼头命令间隔，主要原因是颈部协调策略按眼球相对正中的偏移决定运动方向，而非按眼球当前运动方向决定；颈部在行程端点时，眼球回转也不会立即触发颈部反向。40ms仅是跨过启动门槛后的等待，不是从眼睛开始运动计算的总延迟。

本次仅离线核查，未改运动代码、参数或启动新动作。此前引用的218/335ms仅为两个重新获取人脸片段的命令间隔，不能代表反向跟随、机械动作延迟或整轮分布。用这些样本解释用户的整体观察不充分。

## 2. 证据及复核方法

本机原始证据目录：`outputs/mojia/right_camera_tracking/neck_acc128_repeat_20261023_150346/`，包含寄存器写入前后记录、运行配置及`tracking/tracking_log.json`。本轮10744条控制事件，`completed=true`，`error=null`。ID32硬件加速度原始128、速度900、P/D/I=16/32/0；软件加减速64计数/秒²、眼球先行40ms。

按日志中每帧的眼球策略输出、权重、状态与时间步长，离线重放`MojiaPursuit`颈部规划，记录启动方向、计时器与滤波状态。重放颈部位置与原始`planned_neck_goal`逐帧最大误差为0计数，复核数据保存为`delay_gate_replay.json`。这复现的是给定历史输入的规划，不是新策略在真机视觉闭环中的效果预测。日志字段`eye_error_x`在这里实际保存归一化眼球策略输出，不能当成原始人脸图像误差。

### 2.2 从正中启动也存在额外延迟

本轮初始眼球目标首次偏离1计数为0.050s；颈部进入启动门槛0.151s，规划开始运动0.201s，首次输出变化2计数0.402s。

按各自初始编码器位置变化至少2计数判断，ID23首次采样0.117s、ID32为0.670s，采样事件相隔约0.553秒。每轴反馈约84ms一次，这不是精确的机械启动时间；也不能把“目标首次变化到编码器达到阈值”的时间全部归因于通讯或舵机延迟，因为期间目标本身仍在缓慢爬升。

## 3. 对应代码及额外影响

`tools/xiaobai_runtime/mojia_gaze.py`的`MojiaPursuit.step`：

1. `eye = applied[0]`来自上一帧眼球**规划位置相对正中的偏移**，不是眼球运动速度、原始图像误差或实际编码器位置。
2. `direction`按该偏移符号及0.14/0.07滞回计算。眼球±60计数时，对应启动8.4计数、停止4.2计数。回转但未越过正中及另一侧门槛时，不会触发颈部反向。
3. 改变方向后才设置`pending`，随后等待40ms，并受120ms时间常数的滤波影响。60Hz离散执行下，40ms通常要等3个周期，约50ms。
4. 连续规划位置被限制在2047±80。已到端点且仍要求原方向时，规划速度为0。现有端点处理没有根据目标反向意图提前改变协调策略。
5. 软件加减速仍为64计数/秒²，硬件41改128并没有改变软件这一层。仅按匀加速公式估算，从静止积累2计数就约需0.25秒；这是量级说明，实际还受取整、目标合并、滤波、速度需求影响。
6. `NeckCommandScheduler.step`要求目标变化至少2计数且距上次更新至少40ms才更新目标，进一步延后可发送的首个小动作。两处40ms是不同的条件。

速度900是写给舵机的运行速度上限，不等于软件规划实际速度。当前接力增益120、停止带0.07，归一化偏移最大1时，跟随速度需求最多`120×(1−0.07)=111.6`计数/秒，还要经过软件加速度和端点制动约束；本轮记录的最大规划速度约101.65计数/秒。

ID32采样位置与同帧目标的绝对偏差P95为8计数、最大12计数。设备死区、P及机构响应仍可能影响小动作的可见起点；现有反馈不能确诊全部物理延迟。但8秒样本中，程序在绝大部分等待时间内尚未要求颈部反向，已经足以确认该段主要延迟来自上游协调策略，不能主要归因于总线、D或硬件加速度。

## 4. 下一步改进方向（尚未实施）

优先改眼头协调的方向判据：结合持续的图像目标运动/误差与眼球回中需求，允许在确认目标反向后提前给颈部减速、反向意图，尤其处理颈部到端点后的反向恢复；不能简单把所有眼球回转都当作人脸反向，因为眼球还会补偿头部运动。

保留已认可的眼球参数和当前硬件PID作为对照，增加门槛状态、期望速度、端点状态和图像时间戳诊断，再独立评估软件加减速64是否过缓。验收分别记录目标启动、实际发送、编码器启动、端点反向恢复和停止后抖动，不再仅用`eye_lead_s`代表响应效果。没有依据仅靠把40ms继续减小或继续提高硬件加速度解决已确认的秒级等待。
