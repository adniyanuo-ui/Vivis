# Qwen-Audio-3.1-Realtime纯语音测试

## 1. 范围

本测试独立运行，只使用DOV麦克风、USB音箱和网络，不打开串口、相机、A2F或节目管理器，不要求机器头上电。现有P1语音切换和运动参数保持不变。

当前先测`qwen-audio-3.1-realtime-plus`，`smart_turn_v2`，正常语速1.0、情绪增强开启。首个音色`longanyang_v3.1`（官方“阳光大男孩”）；候选`longshao_v3.1`、`longze_v3.1`。音色说明不是本站听感验收，需现场试听。人物身份读取选定robot.json，小帅为20岁、北京男青年；提示明确标准普通话，不刻意使用重方言。

4. 不发送密钥给协作者，不放入Git或命令行参数。当前程序可交互读取本次密钥，不保存；也可使用当前终端的`DASHSCOPE_API_KEY`环境变量。

首次准备本地依赖（当前Orin已准备）：

```bash

```


```bash

```

## 3. 开始聊天

先Ctrl+C退出旧P1、歌曲及其他占用麦克风／音箱的程序。保持日常使用的音箱音量及位置，首次站在距麦克风约0.5～1米处，先不要改变摆位。这个距离是测试起点，不是模型保证范围。

```bash
./tools/test_realtime_voice.sh --region beijing --ask-key --seconds 600
```

等待“纯语音聊天已就绪”。直接说话，不需要先喊唤醒词。默认10分钟自动结束；运行会调用百炼在线服务，实际用量记录在日志，未设置任何自动充值或无限重连。

- Enter：本地停声并尝试取消进行中的响应。
- Ctrl+C或输入`/quit`：退出测试，释放音频。
- 输入`/mark echo_only`等：标记测试阶段，只写日志，不修改麦克风或模型行为。

按下面顺序观察，建议总计5～10分钟：

| 阶段 | 你的操作 | 重点反馈 |
|---|---|---|
| 男声与人设 | “介绍一下自己”“讲个短笑话” | 男声是否年轻、普通话是否自然、语速是否正常、是否油腻／机械 |
| 情绪回应 | “今天有点累，事情都不顺” | 是否理解和安慰，有无僵硬追问或强行搞笑 |
| 仅自播 | 先标记`/mark echo_only`，请它讲30秒左右故事，之后你保持安静 | 是否把自己的声音转写成用户话语、自我接话或自行打断 |
| 有效打断 | 标记`/mark barge_in`，它说话中间正常说“等一下，换个话题”或“先别说了” | 多久停声、是否残留旧话、能否接上新话题 |
| 附和与旁人 | 说“嗯”“对”，另选短时段让旁人讲话 | 是否不必要地抢话／停声；记录当时具体说了什么 |

若出现反复自我接话，先Ctrl+C终止该轮并保留日志，不让循环持续消耗服务。

换音色需要新建会话（voice只在首次配置时生效）：

```bash
./tools/test_realtime_voice.sh --ask-key --voice longshao_v3.1 --seconds 180
./tools/test_realtime_voice.sh --ask-key --voice longze_v3.1 --seconds 180
```

按顺序分别运行，不同时运行。当前认可的Qwen3-TTS Dylan缓存没有替换；新云端音色单独验收。

## 4. 回声对照和记录

默认`--aec on`复用现有AEC参数，播放期间持续采音，不用关麦规避双讲。参考来自实际输出回调的PCM，包含音量与退出淡出；按DAC／ADC时间戳对齐后再处理。参数来源仍为speech.json，不修改P1源文件。

如果默认测试可用，再在相同摆位、音量和提示词下做短时原始输入对照：

```bash
./tools/test_realtime_voice.sh --ask-key --aec off --seconds 120
```

关闭AEC时上传下采样的原始麦克风音频，用来观察模型／轮次策略自身的回声表现。对比结果依赖现场条件，不能把“偶尔没自我接话”当作已经消除回声。

默认只保存事件、转写、用量及数值统计，不录制PCM。若愿意保存本次声音供分析，在运行命令后加`--record-audio`，会保存三份16kHz、同帧对齐的WAV：麦克风、实际播放参考、上行音频。只记录本客户端完成发送的帧；这不代表服务端已逐帧确认接收。文件只保存在本机outputs。

## 5. 日志及测量边界

每次输出到`outputs/realtime_voice/时间戳/`：

- `effective.json`：公开有效配置、输入／输出设备选择，不含密钥。
- `events.jsonl`：服务端事件、用户／机器人转写、阶段标记、音频数值、首包和实际DAC时间；不保存Base64音频或请求Authorization。
- `summary.json`：错误、响应记录、用量、回调告警、取消操作／响应数量、拒收旧音频包等；取消操作数不等于用户打断次数。

从服务端`speech_stopped`到首包／首个DAC时间是客户端可观测阶段耗时，不能直接称为用户说完到听见声音的完整端到端延迟。`speech_started`到本地取消／缓冲排空同理，不含上行和服务端检测之前的时间。40ms是客户端淡出配置，不是实测总打断延迟。

当前按官方示例在`speech_started`时清除旧播放队列并淡出，拒绝该response_id的迟到包；语义轮次也可能出现`turn_invalid`。因此现场“嗯”导致停声时，要同时看服务端是否真正cancelled，区分模型轮次判断与客户端即时停声策略。服务端自动打断时不再额外发送response.cancel，避免取消新响应；Enter显式取消单独记录。推理完成事件不会丢弃仍待实际播放的音频。

## 6. 首轮真实聊天结果：回声未通过

`outputs/realtime_voice/20261108_150902_734456/`运行约119秒，实际发送5951帧，设备回调无告警，最后由用户结束，无程序异常。25个回答中，出现以下连续自播转写：

- 机器人：“今天过得怎么样？”；下一轮输入转写：“你好呀，今天过得怎么样？”
- 机器人：“我挺好的……”；下一轮输入转写：“我挺好的。”
- 机器人：“这就是默契！”；下一轮输入转写：“没错，这就是默契。”

用户报告机器自己聊起来，转写链也表明自播声音进入了用户话轮。启用AEC及参考覆盖率高不代表回声已消除；本轮回声验收失败。不能据此单独评价男声或情绪交流质量。

客户端因`speech_started`实际裁掉21次旧播放队列，累计丢弃约51.66秒尚未播放的音频；服务端`response.done`均为completed，取消数为0。这符合服务端很快生成完回答、客户端仍在播放时被新话轮切断的情况。25次回答各只有一次playback_started，现有记录没有反复缓冲排空后重启的证据；本轮断续感主要与回声触发的本地误打断一致，不能直接归因于网络。

保留三份同帧WAV用于离线分析。麦克风与参考波形的主要相关峰延迟从约94毫秒变化到约102毫秒；这是该录音中的相关性估计，不是独立测得的声学传播延迟。相同录音用SpeexDSP复算，参考延迟0／60／80／90／94／96／100毫秒未产生全程一致改善，因此没有修改现有AEC配置。没有隔离的纯自播／用户双讲真值，不把分段RMS衰减当作ERLE或双讲通过证据。数值记录在`outputs/diagnostics/20261108_realtime_echo/`。

后续先单独验证音频前端：短时仅自播、用户安静，再验证正常插话；若现场有耳机，可先用耳机隔离音箱到麦克风的声学回路，单独评价云端音色和对话。耳机对照通过也不代表开放音箱的AEC通过。不能用播放期间关麦或忽略全部speech_started来掩盖回声，否则失去真正的双工打断能力。

## 7. 音频前端专项：AEC3候选及本地对照

新增可选`pywebrtc-audio==0.2.0`，在Orin的ARM64/Python3.12独立语音环境中安装并运行。来源、wheel摘要和许可说明见[native/speech](../../native/speech/NOTICE.md)。使用该封装的AEC3和NS，AGC关闭；这是候选实现，不把封装的功能说明当作本站双工验收。P1及本纯语音脚本的默认Speex配置未替换，AEC3需显式选择；本地前端检查默认使用AEC3。

先运行不联网的67秒采集。它使用现有男声缓存作参考，三个阶段之间有静音间隔，持续采音并保存本机录音，不打开串口／相机：

```bash
./tools/setup_realtime_voice.sh
./tools/check_voice_frontend.sh
```

按终端文字提示：用户单独说话10秒、仅音箱播放30秒、双方同时说话15秒。固定短句为“小帅，请停止说话。今天阳光很好，我想和你聊一聊。”双讲时立即重复读，不要等音箱说完；此处“停止说话”只是录音内容，不会触发任务控制。使用`--stage double-talk --seconds 30`可只补测双讲；单阶段另有前后各3秒安静时间。`--aec-backend speex`可对照，`--check`不打开设备。

录音目录为`outputs/voice_frontend/时间戳/`。三份WAV同帧对齐，`frames.jsonl`记录每帧ADC时间与样本索引，`summary.json`保存阶段、处理耗时、回调告警和设备信息。若用户没有按某阶段说话，用单独`annotations.json`记录事实，不改原始录音，不把该段当作双讲通过。

同一录音离线对比，避免两次现场环境不同造成误判：

```bash
PYTHONPATH=src outputs/speech/venv/bin/python -m vivis.speech.voice_analysis \
  outputs/voice_frontend/实际时间戳 --replay speex aec3 --transcribe
```

输出到该录音的`analysis/`新目录，已存在则拒绝覆盖。复算只读取16k录音，不重复下采样；原始现场DSP则使用相同的连续48k→16k滤波及所选前端。转写只使用现有本地SenseVoice作辅助诊断，不调用付费API，不用其转写替代云端Qwen验收。分段RMS衰减、相关峰不是ERLE；双讲时RMS下降也可能意味着用户声音受损，必须核对固定短句。程序默认不为用户传入未录制音频作假设。

临时音量对照：本地检查和云端试验均支持`--output-gain 0.5`，只调整该进程的数字幅度，实际参考包含该增益，不改ALSA系统音量或配置文件。默认仍读取realtime_voice.json的1.0。

## 13. 短促回应造成已收到语音被永久截断

用户对183656云端试验整体反馈“效果非常好，满意”，但报告火锅／烤肉这句后半段没有播放。核查`outputs/realtime_voice/20261108_183656_434588/events.jsonl`与effective配置：实际命令只指定region／profile，沿用600秒、幅度1.0，未开启录音；不能当作原计划120秒、幅度0.5或已保存云端音频的测试。

这句已收到19包，共7.28秒音频，云端response.done状态completed。随后118094.901564秒的speech_started触发原客户端永久取消，丢弃275520个48k样本（5.74秒），只保留40ms淡出。118098.174559秒，同一item的speech_stopped返回turn_invalid，相隔约3.27秒；原实现只计数，没有恢复机制。用户明确确认当时有短促回应，并非想打断。这是播放器处理无效轮次的明确缺陷，不是根据音量推测AEC失效。

[官方事件说明](https://help.aliyun.com/zh/model-studio/qwen-audio-realtime-server-events)明确turn_invalid属于无效轮次。修复保留实时麦克风／AEC和原音频参数，改为：

1. speech_started立即淡出并暂停，保留原有有界缓冲及后续同响应音频，不等语义结果才停声。
2. 匹配同一item的turn_invalid，淡入续播保留的剩余音频。
3. 有效speech_stopped、input committed、新response或服务器明确cancelled，按响应ID清理旧音频；新回复不得被旧事件误伤。
4. Enter手动停止具有最终效力，迟到invalid事件不得恢复；多个疑似轮次也只处理当前匹配item。

新增provisional_interrupt／invalid_turn_resume及实际DAC暂停／恢复日志，汇总暂停和无效恢复次数。原30秒缓冲上限、麦克风持续采集和真正打断的立即停声保持。若服务端已取消生成，不能恢复它尚未发送的语音，不自动调用付费重生成。该修复不保证短促回应完全没有短暂停顿；云端判定无效后才续播。

验证：原HEAD运行火锅时长回归会失败；修复后10项针对性测试通过，覆盖5.74秒尾音保留、真实打断、手动停止、迟到事件、回复切换、部分淡出及有界暂停缓存。完整离线检查489项通过（3项可选依赖跳过）；其中后补的2项已在针对性测试单独通过。独立检出相关22项通过。尚未重新连接云端验收修复。
