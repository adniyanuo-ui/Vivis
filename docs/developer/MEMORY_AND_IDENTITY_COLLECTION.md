# 专项三、四：聊天档案与身份样本

本轮目标是让下一次交流接得上，并在正常聊天中积累可靠的认人样本。运动参数、音色、口型增益和留言权限沿用已验收版本。机器头断电期间完成的是离线验证，实际认人准确度与现场自然度另行验收。

## 1. 保存什么

| 对象 | 本轮规则 |
|---|---|
| 熟人近期档案 | 每人最多500轮。用户定稿文字、用户录音、关联回答文字、实际送往音箱的回答录音和播放结果。 |
| 陌生人近期档案 | 共用other类别，合计最多5000轮；按来访会话分开，不合成人物背景。 |
| 长期记忆 | 从本人原话提取有用事实，保留来源、原话、日期和更正历史。不会把机器人的猜测当作人物事实。 |
| 留言和取件码 | 继续使用独立业务账本，不参加聊天轮数的覆盖。 |
| 主动欢迎、准备提示 | 作为会话事件记录，不冒充用户说过的话；单独保留最近5000条事件。 |

“定稿”指云端返回的最终识别文字，不是识别过程中不断变化的半句话。一句用户话语是这一轮的起点；关联回答真正播完、被打断、取消或失败时记下结果。工具调用可能使一轮有几段回答。没有回答也会留下“未回答／连接中断”等结果，不用下一位用户的话补齐上一轮。

待机中未唤醒、未接纳的旁人语音不计入来访档案；声纹参考也要等该话轮的定稿正式接纳后才积累。原有诊断日志与新聊天档案是两回事。

用户音频按发送给云端的音频偏移映射回本机采音时间，不能用网络事件到达时间裁切。机器人音频取自现有播放回调，包含音量和淡入淡出的实际输出。记录的是送往DAC的样本，不是现场声压测量。长节目仍由原节目日志记录，不把整首歌曲重复存成一段聊天回答。

对被打断的回答，保留生成文字及实际播放状态；没有强行猜测“听到了文字里的第几个字”。偏移缺失、队列丢帧、进程中断和短语音恢复均有明确标记，不能当作完整录音。

### 新旧库的边界

新音文档案在`private/continuity/rounds.sqlite3`，录音在其`audio/`下。原`private/memory/conversations.sqlite3`及其业务表保留，首版不迁移或删除旧库。500／5000是新音文档案的轮数，不是原库历史行数；原库兼容文字仍保留，后续若清理它，应另做迁移验收，不能删掉留言来源证据。

首次启用时冻结旧库的历史来源边界，管理员整理档案也会读取这部分已有的熟人用户原话；只读，不回写原库。之后的新轮不作为“旧历史”重复归档。

熟人到500轮时，只有最旧轮已经整理，才允许新轮覆盖它。尚未整理就暂停新增完整记忆，保留旧资料，日志及模型上下文明确说明未保存，聊天和留言仍可进行。没有增加100轮文字缓冲。陌生人不做长期人物归档，正常滚动到5000轮。原库与本次新档案须分别备份；都在忽略目录，不推送GitHub。

## 2. 怎样整理档案

何工身份确认后，在交互态说：**“请整理档案。”**

1. 程序核验本轮定稿话语和管理员身份，回应已接收，然后回待机。
2. 待机中按人、按小批原话整理。只让原有在线Qwen做文本提取；不打开新麦克风、音箱或相机。
3. 程序校验事实的来源和摘录，使用短事务提交；成功批次留下检查点。
4. 全部提交后，才播报**“档案更新完毕。”** 失败则播报具体原因，原始记录保留。

新访客进入交互时，让接待优先；未提交批次暂缓，下次待机继续。进程重启后从已提交检查点继续，不重复生成事实版本。播报失败不撤销已提交档案，也不谎称已经播报成功。首版没有午夜自动整理。

长期事实采用“简短事实＋本人原话＋日期”的形式，避免另写一段无法核验的自由摘要。后续明确更正会产生新版本，旧值及来源仍保留。聊天只注入当前人的有限近期原话和有效事实，新更正优先于旧摘要；不把所有人的500轮一次性发送，也不拿历史约定执行新任务。

## 3. 照片怎样悄悄积累

复用现有SeetaFace识别和相机进程，不开第二个摄像头。

原身份识别流程 → 可靠单人身份连续稳定约1秒 → 采集质量、原始人工照片再次核验及去近似重复 → 选取不同角度和光照 → 先补活动区，再补候选区。额外1秒只决定能否采集，不延迟认人、回应或业务。

正常聊天采集起测值（2026-11-24）：

| 采集项 | 之前 | 当前 |
|---|---|---|
| 可靠单人稳定观察 | 2秒 | 1秒 |
| 人脸裁剪最小边 | 90像素 | 60像素 |
| 清晰度（Laplacian方差） | 45 | 25 |
| 归一化灰度均值范围 | 0.15～0.90 | 0.10～0.95 |

这些值仅在`configs/perception/familiar_faces.json`的`photo_sampling`中配置；其他旧配置未提供时保留历史默认。每0.75秒的采样间隔、最长30秒的一批提交、原始人工照片比对、近似去重、32张总额／16张活动、人工锁定均保留。原Seeta识别质量和身份确认／业务保持流程不变。降低附加采集门槛后，仍需人工在8766页面剔除不理想的样本；不承诺每一轮聊天都产生新照片。


每位熟人最多32张登记原图，前16张活动、后16张候选；人工上传和手动激活的照片锁定在活动区。优先补满活动16张，再补候选16张，不为凑数接纳低质量或近似重复图片。满32张即完成采集，自动流程不替换现有照片，没有每日限制，也没有减半更新。人工删除多少，后续只补多少空缺。熟人识别和聊天不需要等采满32张。

合格图片在内存里攒一批，最多约30秒，空位已攒齐时提前提交；后台整体保存照片和清单，完整提交后才更新识别图库。写盘忙时，识别读取原完整快照，不等待写盘锁。没有重新打开相机或增加身份推理。8秒逻辑身份保持不作为采集凭证；复核中、多人、低质量或仅凭保持身份的画面不能采集。中断后的未保存候选可以丢弃，已经提交的照片和满额结果重启保留。

认人耗时要分开看：首次确认仍需连续两个合格结果；8秒用于已经认出后的丢失／换人保持，不保证8秒内一定认出。常驻视觉在待机、交互、节目期间均继续认人，节目配置省略熟人识别字段不会暂停它。普通`other`访客可以聊天，私人记忆和留言另按身份授权。

如果画面有人却一直`other`，先查看`persistent_vision/vision/detections.jsonl`内的`metrics.familiar_identity.observation`。`quality_rejected=true`说明图片在比对前被筛掉，不等于模型认错。`quality_rejection_reasons`区分亮度、清晰度；亮度不合格还附带`brightness_diagnostics`，提示过暗／过曝及所选人脸区域的统计值。该统计只辅助诊断，不替代原模型决定，也不自动改变曝光、识别阈值或登记照片。先用单人、正面均匀光照对照，再判断是否需要调整相机。

目前已核对的人工基础照：何工1、井明1、小梁1、戚主任3、小王1、魏宇飞4，全部保留。固定的人脸A/B测试视频继续作为独立验证素材，不混入训练样本。

私有目录按稳定ID保存：`private/people/heyude/photo_pool.json`等；`private/people_by_name/`提供姓名入口，指向同一份资料。`photo_pool/`中的新原图及清单可直接在Orin文件系统查看。清单包含活动hash和锁定标记，不另外复制16份照片。

管理员发现错样本时，先看清单：

```bash
.venv/bin/python tools/manage_photo_pool.py --person heyude
```

从候选中替换一张活动照片，用上面清单的完整hash：

```bash
.venv/bin/python tools/manage_photo_pool.py --person heyude \
  --activate 候选照片完整hash --replace 错误活动照片完整hash
```

被替换的自动照片保留在候选区并排除后续自动入选；基础照片不能用该命令替换。正常采样无需人工逐张审批。

只想暂停使用一张活动照片、不立即指定替代者，可用：

```bash
.venv/bin/python tools/manage_photo_pool.py --person heyude --deactivate 活动照片完整hash
```

这会保留原图，将它移出活动子集并标为已停用。停用不删除图片、不腾出32张总额，因此满额时不会重新采集；可以从候选中选一张补进活动区。活动未满16张时，可单独激活候选：

```bash
.venv/bin/python tools/manage_photo_pool.py --person heyude --activate 候选照片完整hash
```

满16张时请用前述`--activate ... --replace ...`原子替换。手动激活立即锁定，自动流程不会撤掉；管理员仍可停用或删除自己激活的自动照片。人工上传的原始基础照继续保护，变更需单独重建登记。

永久删除一张自动照片，清单与文件同步更新，随后只补该空位：

```bash
.venv/bin/python tools/manage_photo_pool.py --person heyude --delete 照片完整hash
```

已有活动照也可用`--lock 照片完整hash`明确锁定。以上管理命令在现有识别任务之间生效，不重启相机。若直接从文件管理器删除`photo_pool/`内的自动照片，需重启服务后核对清单；启动时会移除缺失原图的对应自动特征，恢复空位。推荐用`--delete`，避免等待重启才同步。

## 4. 声纹先观察，不办事

使用本地中文CAM++模型，CPU单线程；模型和声纹特征不上传云端。参考[官方部署说明](https://k2-fsa.github.io/sherpa/onnx/speaker-identification/)及[模型发布页](https://github.com/k2-fsa/sherpa-onnx/releases/tag/speaker-recongition-models)。

正常聊天时，从至少0.6秒的清晰有效语音中提取候选（2026-11-24用户再次将0.8秒调为0.6秒；仍按超过原能量门槛的帧累计，不含首尾静音）。太短、太轻、削波、机器人正在明显出声、分段音色不一致等情况跳过。参考采集改为下述独立短句聚合；至少3条相互一致、来源不重叠的活动参考后才有个人候选，每人最多32段参考录音及特征。采满后停止新增，不滚动覆盖、不按天重置；声音候选仍继续观察。自动质量门控不能保证排除一切多人混说，因此本阶段绝不赋权。

参考录音在`private/speakers/人物ID/样本ID.wav`，原单轮样本保留原话轮ID，新聚合样本使用`agg_`前缀。可在8766页面试听、停用或删除。下次观察同步移除缺失WAV的特征，后续只补空缺，不替换剩余样本。这32段是声纹参考样本，与500／5000轮正常聊天录音分开；不会因声纹采满而停止保存聊天。

### 4.1 短句怎样积累参考（已实现，尚待现场验收）

采样与当前句认人分开：当前句不足0.6秒仍不确认声音身份，但同一人的可靠片段可以暂存在后台。只在该原话轮定稿被正式接纳后采集，不把未接纳的旁人聊天放进参考。

1. 每0.2秒旁路查看原视觉输出，只取新鲜的单人、已确认画面；不沿用8秒业务保持身份。每个原画面最多为其后0.5秒提供采集证据，下一次未确认画面即截断，不能用一次认脸覆盖整段未知声音。原有起止均核验通过且中途无冲突的完整话轮仍可使用。
2. 每个片段最少0.2秒有效发声，仅准许进入暂存；排除机器人实际输出及前后100ms邻近片段，保留原能量、削波门槛。缺失回采参考的区间不当成静音。图像看不清时暂停加入，已有片段暂存，不用声纹自己的猜测给自己登记。
3. 同一人的短句在最多30秒内累计，先试1.5秒有效发声。多原话轮组成的参考必须通过两个独立片段的声音一致性检查，阈值仍为0.6；与已有本人活动参考中心仍须至少0.65。未通过时可再等新短句，每次增加约0.5秒证据，最多试到3秒；达到上限仍不可靠就丢弃该组。整组音频最多12秒，不因安静时段无限增长。
4. 新确认人物、多人混入、图声确认冲突、采音话轮失效、视觉进程更换或超时，丢弃旧暂存组。确认声音与图像不同时，不为图像人物增加该轮声音参考。新样本不改变原聊天记录的说话人。
5. 一组只保存为一段参考，保留每个原话轮ID、原会话、片段偏移和图像证据时间。原话轮不能再参加另一份已提交参考；进程重启后仍从图库来源核对。文件和清单成功提交后才报“声纹聚合参考已入库”，暂存与失败分别显示。

后台仍为单个可跳过任务、无等待队列，不等待采样才能聊天；忙时可以漏采。满32段停止新增，停用仍占32段名额，人工删除才腾空；不自动替换。`short_collection.enabled=false`可回退原单轮起止核验采集，其余阈值保持。

起测日志示例：

```text
声纹短句暂存：何工，有效发声0.48/1.50秒，来自1轮；尚未入库
声纹聚合参考已入库：何工，7/32，来源4轮
```

1.5秒是尝试入库的起点，不保证达到即通过。独立临时库中，将既有6条何工录音各裁出500ms作开发回放，累计2.3秒仍未形成可靠参考，原库未新增；这说明音色与语音内容差异仍需现场验证，不能只凭时长宣称识别率提高。该回放不是现场连续短句验收，也未把历史录音自动录入正式图库。

日志先显示原有逻辑身份和实时图像身份，再追加声音候选；声音通常晚一点返回，单独注明原话轮。例如：

```text
何工-何工/图-other/声（识别）：今天想聊聊篮球。
语音提示：声纹观察［原话轮xxxxxxxx］：何工-何工/图-何工/声；accepted
```

声纹不能改变逻辑身份，不能因此读取私人背景、记忆或转交留言，也不能把迟到结果挂到当前另一位访客。快递员按委托人姓名或手机尾号核对的原规则不变。现有旧录音缺少可靠的音文边界与本人证据，不自动拿它给某人建声纹；本轮只用未标注旧音频做模型加载和特征提取检查。

当前比对方法：合格录音用本地CAM++提取192维特征并归一化；每人至少3条活动参考，将参考向量取平均后再次归一化作为人物模板。与各人物模板算余弦相似度，第一名至少0.65，且比第二名高至少0.12，才输出声纹候选。这些分数不是识别概率；0.6秒有效发声门槛与无量纲相似度0.6／0.65也不是同一项。

长于等于5秒的观察另做分段声音一致性检查。`consistency_window_mode=speech_aligned`只把检查窗口对准超过原能量门槛的发声边界，保留100ms上下文，两段互不重叠、各最多2.5秒，且每段满足当前有效发声最小值；两段特征相似度仍须达到0.6。整句主特征与原录音不裁剪、不重写，旧参考特征不重建。设为`fixed`可回退旧固定首尾窗口；旧配置没有该字段也走fixed。检查不通过时，即使整句与某人很像，也不发布身份候选，不新增参考。

日志现在区分“音频质量通过”“匹配通过”“相似度不足”“候选差距不足”“分段不一致”；`accepted`不能单独当作认人成功。例如“候选何工，相似度0.592低于0.650”仍是未确认；“声纹匹配通过：何工（仅观察）”才表示该次通过。左侧逻辑／图像身份仍由原视觉流程决定，因此`other-other/图-何工/声`是允许的观察结果，不会自动授予权限。新增参考使用4.1的独立视觉片段证据，不能拿声纹的猜测给自己增加样本。

### 4.2 短句实时认人与图声融合（建议，等待确认，不在本轮启用）

逐句观察不等待参考攒满：当前句够用则先判，太短返回None；近期同一说话人的几个短句可另设短时识别窗口，累计约1.5～2秒有效语音后复核。不能将采样30秒窗口直接当实时识别窗口，也不能把无法判断是否换人的声音盲目拼接。窗口需绑定原话轮与来访，对换人、双讲、冲突及失效清空；不能把迟到结论算给当前另一个人。

拟明确四种结果：确认A、疑似A、other（可用证据比对不到熟人）、None（无合格结果）。Seeta疑似0.40、CAM++疑似0.45仅为待实测起点，不是概率，也不直接授予身份；确认门槛和区分第二名的条件保留。两路相同疑似可作为联合证据，但须对齐时间、验证独立误认，不能认为两票一定正确。

业务身份建议：确认优先；双确认冲突按用户要求采用图像且该轮不采声音；两路同疑可确认；两路other清空；仅弱证据且命中历史人物时保持，否则other。两路None保持当前；**一路None而另一路确认时，建议采用确认路**，否则背对相机时声音确认也无法发挥作用。这与“一路None一律保持”的字面规则存在冲突，需用户确认后实现。到访真正结束时另行清理，不让旧身份无限沿用给下一位。

每轮记录与业务请求的身份一经接纳即固定；后到结论只影响后续交互。图像优先是本场景的用户选择，不能证明镜头外发声者就是镜头前的人。本轮只实现4.1，未改变业务权限、8秒保持或当前日志的other表示方式。

更换部署机时准备可选模型：

```bash
.venv/bin/python tools/setup_speaker_observation.py
.venv/bin/python tools/setup_speaker_observation.py --check
```

## 5. 配置和排查

| 配置 | 用途 |
|---|---|
| `configs/interaction/p1.json`的`realtime_voice.continuity_config` | 新档案入口；设为null关闭本轮音文／声纹旁路，恢复原有文字记忆行为。 |
| `configs/interaction/continuity.json` | 500／5000限额、管理员、归档批量和超时；不设100轮缓冲或午夜任务。 |
| `configs/perception/familiar_faces.json`的`photo_collection` | 关闭自动补充照片；原来的识别功能保留。 |
| `configs/perception/speaker_observation.json`的`enabled` | 关闭声纹旁路。`observation_only`必须为true。 |

修改配置后统一重启服务，避免运行中的参数来源不一致。照片活动子集的受控更新无需重启。录音和照片会占用本地磁盘，正式长期运行还需观察真实平均语音时长及磁盘使用，不把“500轮”误当成固定MB数。

只读查看统计和最近原话轮：

```bash
.venv/bin/python tools/check_continuity.py --person heyude --last 5
```

此命令不打开设备或连接云端。可查轮数、归档任务、音文路径、实际播放状态及照片／声纹数量。返回文字属于私人资料，不应截图公开传播。

### 在Orin显示器上点击管理照片与声纹

在Orin本机浏览器打开 **http://127.0.0.1:8766/**。`8765`人脸跟随／交互日志页面也有入口。审核服务独立运行：机器头断电、交互服务暂停时，仍能看照片、试听和管理样本。

新机器首次安装：

```bash
.venv/bin/python tools/install_review_service.py
```

安装后随Orin开机启动。不安装系统服务时，也可用`.venv/bin/python -m vivis.interaction.review_server`临时运行。页面只接受本机访问；照片、录音及操作不发到云端。

1. **停用**：保留原文件，不再参与识别；不会释放32个采集名额。
2. **激活**：候选照片仅提供“激活”和“删除”。活动照片不足16张时，激活后加入并锁定；已满时提示“激活照片已满16张，请先停用部分照片”，不改变清单。先在活动照片中停用，再激活所需候选照片。基础照片保持锁定。
3. **锁定／解锁**：人工激活会自动锁定。解锁不等于停用，照片或录音仍参与识别；现有填满即停规则也不会主动覆盖它。
4. **永久删除**：从清单和磁盘删除所选样本，自动采集只补空缺。基础原图不提供在线删除；若需重建基础登记，仍走人工登记流程。

声纹录音提供同样的按钮和试听。没有16／16分组；最多32段全部参考，停用后只用剩余活动样本，至少3段独立活动录音才可显示候选身份。声纹仍只观察，不授予业务权限。操作结果会显示在页面顶部；清单被后台采集或另一个页面更新时，旧操作会要求刷新，避免覆盖新结果。样本变化在后续识别任务间加载，无需重开相机。第一次部署本轮代码需重启交互服务一次。

页面下方还可查看每位熟人最近10轮音文与回答状态。普通聊天录音与声纹参考是两份清单，聊天录音不能因为听起来清楚就自动赋予某人的身份。

看照片不用暂停交互。**通过Orin音箱试听前先运行`sudo systemctl stop vivis-p1.service`**，避免小帅把回放当成新话语；听完用`sudo systemctl start vivis-p1.service`恢复。浏览器回放不经过交互系统的DOV参考输出。也可用耳机。

原`tools/manage_photo_pool.py`命令继续可用；`tools/review_continuity.py`仍导出只读快照`private/review/index.html`，该快照顶部新增实时管理入口，离线快照不会自动刷新。


### 区分聊天记录、质量通过与参考入库

日志末尾`other/声`仅表示声纹候选尚未确认，不等于没有录音或语音识别失败。普通聊天按500／5000轮保存，声纹参考另做筛选，至少3段活动参考才显示候选。`accepted`表示音频质量通过，只有`reference_sample_saved=true`才表示该参考实际写入；新日志同时显示起止身份不可靠导致的未入库原因，以及有效发声秒数。

交互管理器日志现在明确显示成功结果。启动时先报已有数量，例如“照片样本库：何工，当前32/32；活动16/16，候选16；已采满，停止自动新增”，这不是本次又采集了32张。随后新增原图／声纹WAV及对应清单均成功保存，才显示“照片采集成功：……”或“声纹参考采集成功：……”，包括姓名、新增数、总数和活动数。后台最多约2秒检查一次，日志繁忙时稍后补报，不抢占控制事件；文件缺失、仅质量通过或仅暂存不报成功。照片已满32张时没有新采集日志是正常的。声纹与已有参考不一致会显示“未新增样本”，不代表交互程序故障，也不会自动删除旧参考。

照片识别成功也不等于一定新增原图。采样需要连续可靠单人1秒、足够脸部像素、质量及去重，采满32即停。可在视觉预览“检测详细数据”或`detections.jsonl`查看`photo_collection_last_attempt`，用其人物与原帧时间关联本次尝试：`face_too_small`为脸部尺寸不足，`image_quality_low`附具体亮度／清晰度指标，`near_duplicate`为近似重复。`staged_for_batch`只表示暂存，最多30秒的一批文件成功提交后才会出现在样本管理页。字段是最后一次尝试，不是当前每帧都在采集；历史没有该字段和原图时，不能冒充恢复了旧帧筛选依据。

### 亮度异常图片留存（2026-11-24）

固定目录：`private/diagnostics/face_brightness/`，可直接用Ubuntu文件管理器打开。后台最多每2秒留一张、总计最多100张，满后停止新增，不覆盖；管理员删除部分图片后只补空缺。每张JPG另有同名JSON说明框坐标、原帧时间、亮度及拒绝原因。文件名前面的数值是**所选人脸区域平均灰度÷255**，不是整幅图或房间亮度。

- `0.0824_range-low_…jpg`：人脸平均亮度不在照片采集附加范围`0.10 < 亮度 < 0.95`内；过亮标为`range-high`。范围只读取`familiar_faces.json`的`photo_sampling.brightness_range`。
- `0.1234_native-low_…jpg`：SeetaFace原生亮度等级为LOW。它采用自己的九宫格亮度判据，因此即使平均亮度在0.10～0.95内也可能被拒绝；不能将两种门槛混为一谈。

保存的是相机原帧的JPEG副本，未调亮，不带身份标签，不计入任何熟人的32张照片、不进入活动识别库，也不发给云端。身份未知或个人照片池已满仍可采集诊断帧。写盘在独立可丢弃后台任务中；忙时跳过，失败只记录诊断错误，不改变认人／跟随／业务权限。视觉详细数据中`brightness_diagnostic_samples`可查看本进程新增数、目录图片总数及最后文件名；总数在下一次写入尝试时刷新。
