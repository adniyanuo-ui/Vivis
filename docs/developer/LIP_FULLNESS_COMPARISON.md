# wz2圆唇/嘟唇表现对照

2026-10-28。用户反馈嘴型偏扁，进一步明确为嘟唇、圆口及前突不明显，而非单纯张嘴幅度不足。本轮先改善圆唇轴的位置目标送达，不改原始权重、音频、标定、融合规则、增益或硬件运行参数。

## 1. 已查到的因素

分析会话`20261028_142739_506675_eyes-neck`的wz2两遍记录，口型增益1.0、14个口部轴硬件速度1200，均完整结束。比较源帧名义位置与实际发送目标：

| 轴 | 与名义目标相差超过5计数的控制时刻占比 | 差值绝对值P90 |
|---|---|---|
| 13 | 约30.6%～30.7% | 约64～66计数 |
| 28 | 约27.5%～27.6% | 约46计数 |
| 12 | 约17.3%～17.5% | 约18计数 |
| 27 | 约14.9%～15.1% | 约13～14计数 |

这些是目标与发送命令之间的差异，不是机械跟踪误差。硬件1200速度上限之外，原播放器又用`limit_step`按相同速度逐帧追目标，短促运动可能在软件尚未发到端点时已经反向。

源权重与映射检查：

- wz2的Funnel/Pucker峰值分别约0.755/0.764，圆唇信号并非一直没有。
- 普通归一化在ID31未触发，在12/27约0.6%、13约4.3%、28约0.9%的源帧触发；该数据不支持把整体扁平首先归因于归一化。
- 这些唇部轴的名义轨迹未触及设备位置端点，本轮不扩大行程。
- JawForward峰值约0.21，35号由2047向2247的标定只使用到约2089；这是另一个可能限制下巴前突的因素，本轮保留不变。
- 旧`--mouth-gain`组为12/13/27/28/29/31，不覆盖全部上唇与圆唇轴，不把它当作完整圆唇组增益。本轮继续1.0。

反馈中仍能看到目标与编码器的动态差异，但反馈是分时读取，不能用稀疏反馈最大值代替每次短促动作的真实峰值。最终是否更饱满需用户观察。

## 2. 唯一对照变量

```bash
./examples/03_face_eye_neck_tracking/run.sh --work wz2 --repeat 1 \
  --parallel-neck on --mouth-command-mode lips-direct
```

`lips-direct`从当前标定中提取MouthFunnel/MouthPucker涉及的轴，本机为10/11/12/13/15/25/26/27/28/30；后续经用户确认再加入JawOpen对应的ID31（见第6节）。仅在音频播放循环中，不再先把这些目标按软件速度追赶后发送，直接发送当前源帧的名义目标。

- 准备、35轴缓慢回中、首帧接近仍使用原限速流程。
- 位置目标仍逐帧检查原命令范围；硬件速度1200与加速度设置不变。
- ID29/35/36、眼球与三自由度颈部仍走原链路，Ruckig不变；ID31在第6节扩展前也保留原链路。
- 单一串口拥有者、反馈、温度确认、通信看门狗、Ctrl+C及保持扭矩策略保留。
- 源帧采样/跳采、60Hz/1Mbps及全部素材字节保持，不人为添加停顿或修改口型权重。

这是发送方式对照，不代表舵机可以突破硬件速度，也不代表软件取消后机械一定到位。新模式不默认启用。

## 4. 后续约束与速度对照

用户反馈`lips-direct`在会话`20261028_145423_096719_eyes-neck`中稍稍改善；十个圆唇轴名义目标到发送目标的P90误差均约0.5计数以内。反馈仍有动态差异。用户明确要求只修复明确软件bug，不添加复杂算法遮盖或修缮硬件不足，允许合理提高速度、加速度。尚未交付的口部提前补偿已全部撤下，运行代码不含该功能；不添加闭嘴优先、静音触发或强制停顿归位。

本轮只提供运行速度参数：

```bash
./examples/03_face_eye_neck_tracking/run.sh --work wz2 --repeat 1 \
  --parallel-neck on --mouth-command-mode lips-direct --mouth-speed 1500
```

`--mouth-speed 1500`将当前标定的14个口部轴任务速度从1200提高至1500，包含10个唇部轴及29/31/35/36。所有轴仍经原启动流程写入/核验SRAM46，回中临时速度仍为60；原来的10唇轴直接目标方式保留。已抽查的口部加速度为0，保留其最大加速度语义；PID、最大/运行扭矩、位置限位、增益与源帧均不变。眼球、眼睑和三颈轴速度不变。当前软件与两类舵机都沿用已核验的速度单位/寄存器路径，不改EEPROM。

默认文件仍保存1200；不带新参数或指定`--mouth-speed 1200`的下一次启动会按原流程恢复1200。退出进程本身不保证立即恢复SRAM值，因此以新一轮的启动读回为准。此选项是显式任务参数，不新增口型算法。

## 5. 0001停顿留缝的已知证据

会话`20261028_145532_571999_eyes-neck`使用原`limited`模式完整播放两遍，未开启唇部直接目标。用户观察两遍之间35轴回中时、以及最后一遍结束后都会完全闭嘴。

- 部分时段ID31名义目标已为2047，但其他唇轴仍保持源文件中的表情位移。例如约2.43秒，12约1954、13约2138、27约2133、28约1963；这不是全口部中性目标。源权重含微笑等动作，软件不能仅因音频停顿就认定它们应归零。
- 播放结束没有面部自动回中，只按既定策略卸载ID29。原末帧ID31目标约1994，并非2047。
- 播放后只读抽查：12/13/27/28/31/35稳态位置距当前目标约0～2计数；31目标1994、实际1992。被卸载的29目标记录2047、被动位置2240，已无扭矩。不能把卸载后的被动越过命令范围当作新增软件目标；现有受控启动恢复仍保留。
- 因而“结束闭口”可能涉及舌部持力与唇部机构耦合；两遍之间完整回中则还改变全部口部姿态。需要实物核验舌部中位/预紧及停顿处组合标定，不能据此直接宣称舌部就是唯一原因。

用户再次确认：启动需要先小幅慢开下颌，再收舌，最后完成下颌回中，否则下颌姿态会影响收舌、产生干涉。沿用已真机验证的ID31=1900、速度上限60计数/秒，待ID29回中反馈确认后才进入35轴回中；不会因口部任务速度1500而加快此步骤。代码补齐“ID29仍使能但离开中位”也必须先避让、再收舌的遗漏，不能直接跳到共同回中。新增分支仅离线验证，现场验证仍由用户手动执行。

提升速度可改善短促动作跟随，但不能改变源文件本就未给出全口闭合姿态的事实，也不能修正机械预紧。当前没有证据支持新增闭嘴算法。本轮未自动播放、未现场写入新的任务速度，由用户用同一作品对照观察。

## 7. Funnel/Pucker运行时通道增益1.2

用户确认只放大MouthFunnel与MouthPucker，其他保持。新增显式参数，默认1.0：

```bash

  --parallel-neck on --mouth-command-mode lips-direct --mouth-speed 1500 \
  --round-lip-gain 1.2
```

只在内存中将这两个原始通道乘增益并裁剪到0～1，然后沿用原标定与融合；不是将十轴全部位移直接乘1.2。wz2原始30FPS数据以原字节随包保存为`assets/works/wz2/source.json`，清单核验SHA256，按原保持采样方式扩展到60FPS。先验证增益1.0可精确复现十个相关轴的当前轨迹，再替换这十列；其他列保留，避免改变已接受的眨眼、眉部和下颌等动作。音频、原始JSON、当前派生目标文件均不覆盖。
