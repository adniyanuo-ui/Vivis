# 机电仿生头人工标定与表情驱动说明

**适用方案：35 个舵机，ARKit 52 通道，人工线性映射。**

修订版本：1.1｜2026-10-28。本文作为人工标定与驱动语义的对齐背景；基础公式、当前程序实现和待实施变更分别说明，不因文档修订自动改变运行参数。

核心规则：**以中性位置为起点，计算各表情带来的舵机位移，再按明确的融合规则组合。中性位置只加一次。** 第4.3节给出直接叠加基准，第4.4节说明当前播放器额外采用的归一化规则。

## 1 标定中性姿态与安全范围

### 1.1 确定共同中性位置

人工调整 35 个舵机，使机器人头部呈现自然的中性表情。

对支持中位校准的舵机，使用飞特调试工具，将当前实际位置设为 **2047**，保存后重新上电检查。

注意区分：

- **中位校准**：将当前姿态定义为 2047。
- **发送位置命令 2047**：让舵机转到原先定义的 2047。

本项目约定：中性姿态对应表情变化的零点，舵机位置值为 2047。对于采用 4096 个位置刻度的型号，编号通常为 0～4095；2047 是所采用的中位参考值。

重新标定实际中性姿态后，可以通过中位校准使它仍对应2047。如果新方案保留了不等于2047的零权重位置，必须另行提供每轴中性位置表，不能从某个表情条目的`position`推断共同零位；当前程序对此的支持边界见第6节。

### 1.2 确定舵机安全范围

从中性姿态出发，逐个调整舵机，确定合理的最小、最大位置。避免机构干涉、胶皮过度拉伸和持续受力，并预留余量。

安全范围保存到标定工程；具体型号支持时，将经确认的新范围写入舵机固件的角度限位，并同步运行硬件配置。

新一轮实物复标确认的范围是该轮拟采用的新版本；设备当前读回值只是现状，可能仍是旧版本。落实新标定时应：

1. 确认本次修改的轴、中位、上下限及表情端点，检查同轴在各表情条目中重复保存的限位是否一致。
2. 核验新中位和端点位于新范围内，并完成相关组合姿态验证；存在冲突先核对标定记录，不静默裁剪后声称新标定已完整落实。
3. 保存原设备配置，按相应型号流程更新中位/角度限位；改变坐标零位时，相关端点和限位要属于同一坐标系。
4. 写入后读回核验，需要持久化时完成断电重启核验；同步`hardware.json`中的中位、设备范围和受影响的任务/反馈范围。
5. 核对回中、眼球/颈部跟踪、派生轨迹与来源哈希后，再进行现场验收。

这是一项明确的标定部署任务，不在普通播放或代码整理时自动执行；新的限位得到确认后，也不应因设备仍保存旧值而反向覆盖新标定。

示例：

```json
{
  "descEn": "Middle right eyebrow",
  "descZh": "右眉中",
  "id": 17,
  "minPosition": 1794,
  "maxPosition": 2394,
  "position": 2047
}
```

| 字段 | 含义 |
| --- | --- |
| `id` | 舵机编号 |
| `position` | 当前保存姿态的目标位置；本例为中性2047，在表情条目中则表示该表情1.0的端点 |
| `minPosition` | 允许的最小位置 |
| `maxPosition` | 允许的最大位置 |

**固件角度限位是舵机内部的控制限制，不等于结构上的机械挡块。单舵机不越界，也不代表多个舵机组合运动时一定无干涉。**

## 2 标定 52 个基础动作

参考 Apple ARKit 的动作定义及结构提供的舵机分布图，逐项标定：

1. 将头部恢复为共同中性姿态。
2. 选择一个基础动作，确定它涉及的一个或多个舵机。
3. 逐步调整相关舵机，使真机达到认可的动作强度 **1.0**。
4. 保存该动作的名称、相关舵机编号和对应位置。
5. 检查中间强度、往返动作和回中性能力；完成单动作后，再验证典型组合。

例如，沿用项目中的 `BrowOuterUpRight` 通道名称：

```json
{
  "posSize": 3,
  "positions": [
    { "id": 17, "position": 1794 },
    { "id": 18, "position": 1994 },
    { "id": 19, "position": 1888 }
  ],
  "shape": "BrowOuterUpRight"
}
```

这表示该动作权重为 1.0 时，三个舵机分别到达上述位置；该动作权重为 0 时，不贡献任何偏离中性的位移。

**强度 1.0 是动作的有效标定端点，不等于舵机数值最大值，也不要求到达机械极限。** 例如，17 号舵机从 2047 移到 1794，数值减小，但该动作的强度在增大。

未列入某动作的舵机，对该动作的位移贡献为零。通道名称和大小写通过接口适配统一，不能仅依赖数组顺序匹配。

完成后导出 AFS 和 JSON 文件，检查两者的动作数据及中位约定一致；运行JSON可以不包含限位字段，由唯一硬件配置保存限位。颈部等不属于 ARKit 52 的动作另行标定与控制。

### 2.1 参与关系与显式中位：MouthClose示例

用户已明确本机当前的定义：**MouthClose只涉及ID31，该轴权重0与1.0的目标均为2047。** 可以在运行标定中明确保存：

```json
{
  "posSize": 1,
  "positions": [{ "id": 31, "position": 2047 }],
  "shape": "MouthClose"
}
```

它记录的是ID31的参与关系和零位移端点，不是其余34轴也要主动回中。本文例子用于明确目标语义，本次文档修订没有把它写入当前运行标定。

AFS保存35轴的完整姿态记录，其中未调整的轴也可能是2047；不能仅凭这些记录推断35轴全部参与某个动作。导出时既不能无条件丢掉所有2047而丢失已确认的参与关系，也不能无条件把全部35轴加入融合。此例的ID31参与关系来自用户确认，不能由AFS中的全轴中位记录自动推导。

对直接位移叠加，MouthClose的这一条贡献始终为`w × (2047−2047)=0`；它不会自动抵消JawOpen的开口位移，也不是抢占式回中指令。当前归一化算法中显式条目可能影响分母，见第4.4节。若需要主动闭合或闭唇优先，需要另行明确口部融合/控制权规则。

## 3 单个表情怎样换算舵机位置

### 3.1 中文计算规则

> **目标位置 = 中性位置 + 表情权重 ×（该表情的标定位置 − 中性位置）**

对应公式：

$$
p = 2047 + w\,(p_{\mathrm{标定}} - 2047)
$$

| 符号 | 含义 |
| --- | --- |
| $p$ | 最终目标位置 |
| $w$ | 该表情的当前权重，范围为 0～1 |
| $p_{\mathrm{标定}}$ | 该表情强度为 1.0 时保存的位置 |

### 3.2 计算示例

以 17 号舵机为例：中性位置为 **2047**，某表情的标定位置为 **1794**，当前权重为 **0.5**。

**第一步：计算满强度时的位移。**

$$
1794 - 2047 = -253
$$

负号表示朝位置数值减小的方向运动。

**第二步：按权重计算本次位移。**

$$
0.5 \times (-253) = -126.5
$$

**第三步：加回中性位置。**

$$
p = 2047 - 126.5 = 1920.5
$$

软件按约定取整后发送。

| 权重 | 含义 | 取整前目标位置 |
| ---: | --- | ---: |
| 0 | 不产生该表情的位移 | 2047 |
| 0.5 | 实现一半位移 | 1920.5 |
| 1 | 实现完整标定位移 | 1794 |

## 4 多个表情怎样共同控制一个舵机

### 4.1 中文计算规则

> **目标位置 = 中性位置 + 动作 A 的位移贡献 + 动作 B 的位移贡献 + 其他动作的位移贡献。**

每份位移贡献，都按照上一节的方法计算：**权重 × 相对中性的标定位移**。

### 4.2 两个动作的计算示例

仍以 17 号舵机为例。下面两个动作的数值仅用于解释算法：

| 基础动作 | 强度 1 时的位置 | 相对中性的位移 | 当前权重 | 本次位移贡献 |
| --- | ---: | ---: | ---: | ---: |
| 动作 A | 1794 | −253 | 0.5 | −126.5 |
| 动作 B | 2147 | ＋100 | 0.3 | ＋30 |

先将位移相加：

$$
\Delta p = -126.5 + 30 = -96.5
$$

再加回中性位置：

$$
p = 2047 - 96.5 = 1950.5
$$

**方向相反时部分抵消，方向相同时共同增强。这是第一版线性融合采用的近似规则。**

不能把两个动作计算出的绝对位置直接相加，否则会重复计算中性位置 2047。

### 4.3 完整公式

对第 $j$ 个舵机，将 52 个通道的位移贡献相加：

$$
p_j = 2047 + \sum_{i=1}^{52} w_i\,(p_{i,j} - 2047)
$$

| 符号 | 通俗含义 |
| --- | --- |
| $j$ | 当前计算哪个舵机，例如 17 号 |
| $i$ | 当前检查哪个基础动作 |
| $w_i$ | 第 $i$ 个动作当前做几成 |
| $p_{i,j}$ | 第 $i$ 个动作强度为 1 时，第 $j$ 个舵机的标定位置 |
| $p_{i,j}-2047$ | 这个动作要求该舵机移动多少 |
| $\sum$ | 把各动作的位移贡献加起来 |
| $p_j$ | 该舵机最终的目标位置 |

这里把不涉及该舵机的动作等效为 $p_{i,j}=2047$，因此它的贡献为零；实际软件可直接跳过这些条目。权重为零的动作同样没有贡献。

**52 项只是统一写法，一个舵机实际可能只受到少数几个通道影响。各通道权重之和不要求等于 1。**

上述“跳过零贡献条目而保持结果相同”针对直接位移叠加成立；算法若同时按参与条目计算归一化分母，必须再检查第4.4节的条件。

### 4.4 当前已验收播放器与基础公式的区别

当前`src/vivis/motion/mapping.py`使用`bounded_weighted_deltas`。普通轴先累计位移，再按参与该轴的权重之和归一化：

$$
p_j = p_{0,j} +
\frac{\sum_{i\in S_j}w_i\,(p_{i,j}-p_{0,j})}
{\max(1,\sum_{i\in S_j}w_i)}
$$

$S_j$是当前映射表中列入该轴、并经过控制规则筛选的通道集合。权重和不超过1时，它与直接叠加一致；超过1时，位移被缩小。例：两个动作位移−253、＋100且权重均为1，直接叠加得1894，当前归一化得1970.5。

显式的ID31=2047条目在分子贡献为零，但可能增加参与权重分母；空映射不参与。因此先前两份作品“补ID31=2047”离线试算产生的少量差异来自融合规则，并非新增了闭嘴位移。

眼睑还有独立眨眼合成、重复眼神来源排除等既有规则；在线眼球和颈部跟踪具有独立控制权。不能把普通轴公式当作当前所有轴的完整执行流程。

**直接叠加是本文的基础参考，归一化是当前已验收实现。对齐原则不等于已经切换算法；若要切换，需作为独立修改重新生成受影响作品并做对照验收。**

### 4.5 通道语义与本机映射

Apple将`mouthClose`定义为与下巴位置独立的闭唇系数，并把`jawOpen`作为另一通道。本文确认的ID31零位移映射是本机当前人工方案，不能据此宣称完整实现了所有闭唇肌肉动作。上游两个通道同时非零时如何协调，仍由本机明确的口部融合规则决定，不能通过数组顺序或默认中位记录推断。

## 5 软件执行顺序

每一帧按以下顺序计算：

1. 为每个舵机建立以中性位置 2047 为起点的目标值。
2. 读取当前 52 个表情权重。
3. 根据标定文件，累计各动作对相关舵机的位移贡献。
4. 处理动作冲突，检查舵机限位与组合约束。
5. 按轴的控制权与需要加入平滑和速度限制，最终取整并再次检查有效范围；不要求所有35轴套用同一条轨迹曲线。
6. 将本帧命令按控制协议发送给舵机。

| 验证项 | 预期结果 |
| --- | --- |
| 所有面部动作权重为 0 | 对应面部舵机回到共同中性位置 |
| 仅一个动作权重为 1 | 相关舵机达到该动作的标定位置 |
| 多个动作同时生效 | 位移按规则融合，并满足安全约束 |
| 权重逐渐变化 | 动作方向正确、过渡连续、无明显干涉 |

如果安全限幅、冲突处理或平滑介入，实际发送的位置可能不再等于原始公式结果，这是控制层对目标的必要调整。

表中“对应面部舵机”指由当前表情层控制且允许发送的轴。面部权重全零不能抢占眼球/颈部的跟踪控制权，也不能自动使能未映射或禁用轴；当前ID9、24不参加作品播放位置发送。

## 6 适用边界

本方法是人工标定基础上的线性近似。两个单动作分别标定正确，组合后仍可能因为胶皮和机构的非线性而失真。

先通过典型组合标定与实拍验证改进效果；有明确质量瓶颈时，再增加前向模型和照镜子学习。现有中性、动作和照片记录均可继续复用。

如果某个舵机未统一校准为 2047，应使用它实际的中性位置 $p_{0,j}$，通用公式为：

$$
p_j = p_{0,j} + \sum_{i=1}^{52} w_i\,(p_{i,j} - p_{0,j})
$$

**无论中性数值是多少，计算原则始终相同：中性位置只加一次，各表情只贡献位移。**

上式是通用理论形式。当前墨甲程序仍要求已确认的35轴共同中位2047；引入其他中位数值，需要同步修改输入校验、映射、回中与跟踪中的中位使用，不能只改一个标定字段。

## 7 当前文件的核对状态与使用分层

AFS适合保存标定工程、完整姿态及电机说明；JSON适合保存运行所需的明确映射。两者都是JSON文本结构，信息能否保留由字段与导出规则决定，不由扩展名决定。建议保持：

```text
AFS原始标定工程＋已确认的参与关系/中位
    → 审核并导出运行JSON及硬件配置
    → 设备参数部署、读回一致性核验
    → 表情映射与已声明的融合规则
    → 控制权/组合可达性/实际设备范围检查
    → 舵机目标与现场验收
```

本次检查的`墨甲10.27（19.04）.afs`包含52×35=1820条位置，其中135条非中位映射与同名JSON一致，1685条为2047。仅删除中位条目后得到相同结果，不能证明任意融合语义都等价。

这份AFS还存在端点与自身限位字段不一致，例如ID5的EyeBlinkLeft目标2400而文件上限2320、ID20的EyeBlinkRight目标1747而文件下限1803。文件名相同不足以证明所有字段属于同一轮已确认标定；部署前需要核对复标清单，不能按整份文件无区别覆盖设备。

**本次仅确认并保存背景原则：不写舵机寄存器，不改变当前中位、限位、运行标定、已验收融合算法或两份作品。**
