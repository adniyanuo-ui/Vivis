# 常见问题

版本0.2｜2026-10-26。

| 现象 | 检查与处理 |
|---|---|
| 缺少音频/目标文件、SHA256不符 | 运行`python -m vivis.runtime.assets`核对，核对Git工作区并恢复对应受跟踪资源；不修改哈希绕过校验 |
| 串口权限拒绝 | 检查USB重插后权限及`tools/99-vivis-servo-access.rules`；按错误提示为当前用户授权 |
| dms/ies占用 | 正常停止相应服务后重试，不同时启动其他舵机或相机控制程序 |
| 8765已有不同配置服务 | 查看旧视觉服务的启动终端并正常退出，然后重开示例；不得把未核验相机服务直接复用 |
| 打不开相机 | 检查实际by-id节点；使用`--camera-device`。两眼相机的节点和方向须分别确认，节点编号可能随USB插拔改变 |
| 能框出人脸但真机不动 | 确认运行的是示例2/3，检查控制状态与日志；预览绿框本身只说明检测，不证明串口控制正常 |
| 示例1没有预览 | 正常，面部模式不启动相机；眼球和颈部仅在开头回中 |
| 有声音但口型不同步 | 核对WAV和表情是否同一作品、音频设备与延迟；控制跟随DAC时间轴，不重新生成另一份音频 |
| 回中前位置超出设备限位 | 检查错误中的位置、范围和初始使能状态；未使能的小偏移按`homing.json`复读并限速恢复，较大偏移需先确认实际机构，不扩大播放或设备限位 |
| 收舌时下颌可能干涉 | 启动沿用已验证的顺序：ID31小幅慢开至1900（最高60计数/秒）→ ID29回中并确认 → 35轴回中，包括ID31；舌部仍使能但偏离中位时也遵循此顺序。勿同时直接回中29/31 |
| 收舌反馈2052，接近2047却提示越界 | 当前ID29上限2050；到位必须同时满足中位误差容差与进入设备/反馈范围，连续两次才结束。未使能2055等近中位但越界的状态也先开颌避让；`startup_goal_ready`记录实际判定。保持原恢复时限，不扩大限位 |
| 电机型号或限位不符 | 错误显示实际与预期范围；保存多次读回再对照本体，区分设备寄存器范围和任务行程，不自动改限位适配陌生设备。当前ID32用户确认的EPROM限位和跟踪范围均为1706–2388 |
| 坏包或反馈看门狗停止 | 保存`summary.json`、`preparation.json`、播放日志和串口轨迹；核对接头、供电、总线速率与占用，不反复放宽保护 |
| 播放出现电压/过流/过载/温度告警 | 单次告警继续，按同轴同故障的4个连续有效完整样本决定停播；正常清零。保存`sensor_fault_confirmations`及串口轨迹，检查实际传感器与供电。启动/回中、位置/编码器及通讯保护未放宽，详见[保护策略](DATA_AND_CONTROL_API.md) |
| 重启后参数变化 | 启动阶段会按硬件配置恢复并读回；检查是否存在其他程序覆盖或设备型号变化 |
| 切换500kbps后无法启动 | `--baud`只设主机，先确认全部35轴已完成同速配置及重启核验；当前默认仍1Mbps |
| Ctrl+C后暂时保持动作 | 停止发送不等于切断扭矩，舵机可完成最后目标；本程序保留颈部支撑扭矩 |

新入口测试的日志位于`outputs/developer/`。一份日志只证明对应模式和作品的结果，不能将静态核验、离线通过或中途退出算作整曲完成。

## 交互服务退出时查看具体原因

`code=exited, status=1/FAILURE`只是systemd记录的退出结果。查看此前的应用日志：

```bash
journalctl -u vivis-p1.service --since '10 minutes ago' --no-pager
```

子程序异常退出时，应用会输出`节目故障[故障类型]`、中文说明、原始异常，以及可取得的舵机ID、反馈间隔、控制更新间隔和详细日志路径。例如`CONTROL_WATCHDOG`表示控制目标更新间隔触发保护；它本身不能证明舵机损坏。

摘要同时保存在对应的`outputs/p1/<会话>/<序号>_<节目>.failure.json`和会话的`events.jsonl`（`worker_failure`事件）中，状态界面也显示该摘要。缺少详细记录时会明确提示无法取得具体异常，不推测硬件原因。正常结束和操作员中止不报告为节目故障。

## 相机节点存在，但重新打开或设置格式超时

`camera_setting_start / fourcc`表示最后停在设置像素格式，不单独证明格式配置错误。若内核同时记录`uvcvideo ... Failed to set UVC probe control : -110`，应先排查USB控制传输；设备节点存在、OpenCV报告打开成功，都不能代替实际出帧。

```bash
journalctl -k --since '10 minutes ago' --no-pager | rg 'uvcvideo|tegra-xusb|USB Camera'
sudo systemctl stop vivis-p1.service
ls -l /dev/v4l/by-id/
```

确认交互服务及其他相机程序已停止后，可单独重插摄像头USB；随后用真实运行时采集代码测试，不打开串口、麦克风或音箱，也不保存图像：

```bash
.venv/bin/python tools/check_camera_lifecycle.py \
  --robot configs/robots/xiaoshuai/robot.json \
  --mode hold --seconds 15 --strategy production
```

工具在独立子进程中记录打开、参数设置、首帧和释放阶段。`production`复用`LatestCamera`；`current`保留旧版无条件设置顺序，用于历史对照；`native`只打开和取流。超时或未确认释放时停止后续试次，不在旧驱动操作仍占用设备时并发重试。持续控制超时不能仅靠延长20秒就绪期限解决。

短时恢复后还需分别验证连续取流和多次模式切换，不能据一次成功排除线材、供电、驱动或设备固件问题。仅摄像头测试通过后，再由现场人员启动交互服务；启动会执行原有自检和回中。
